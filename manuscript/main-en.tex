\begin{abstract}
Small SQIsign keys and signatures do not imply a small signing workspace.  In
the SQIsign v2.0.1 Level-I compact implementation studied here, five
simultaneously live regions in \texttt{find\_uv} total \num{6339868} bytes,
exceeding RP2350 on-chip SRAM.  We combine typed lifetime scheduling with an
order-preserving norm sketch that stores a bit length and 64-bit prefix and
regenerates full precision only when required.

For Level I/RADIX32, the operation arena falls from \num{353008} to
\num{172080} bytes (\num{51.2532}\%).  The firmware uses no GMP, dynamic
allocation, or external PSRAM; it reserves \num{321408} of \num{532480} SRAM
bytes and leaves \num{211072} unreserved.  A 100-request differential-
conformance test finds byte-identical output between the ordinary and
low-memory APIs at the same commit; it is not a historical-response KAT.  For
the fixed image, linked call-graph analysis bounds the KeyGen, Sign, and Verify
operation-PSP paths at \num{\VTwoStaticKeygenPspBoundBytes},
\num{\VTwoStaticSignPspBoundBytes}, and
\num{\VTwoStaticVerifyPspBoundBytes} bytes, including one 212-byte exception
entry; handler frames, interrupt nesting, and live MSP use are excluded.

For v3.0, we overlay three lifetime-disjoint pairs in two functions.  The
official and adapted builds pass API, self-test, and official-response checks on 300 distinct
parameter-set/request pairs each, giving \num{600} implementation-vector runs
in total, and all six affected Arm frames shrink.  One commit-pinned
\texttt{p324\_3} RP2350 path reduces the Sign PSP watermark
from \num{\VThreeDThreeOfficialSignPspBytes} to
\num{\VThreeDThreeSignPspBytes} bytes.  These target data cover one parameter
and one deterministic path, not a timing distribution or whole-program stack
bound.  Software timing and trace tests find input-dependent behavior; we make no claim of
constant-time or power/EM resistance.
\end{abstract}

\section{Introduction}
\label{sec:en-introduction}

SQIsign is a Round-3 candidate in NIST's additional post-quantum signature
process\cite{nist-ir-8610,nist-round3}.  It obtains unusually small public keys
and signatures from supersingular-isogeny and quaternion computations
\cite{sqisign-2020,sqisign-spec-v201,sqisign-spec-v3}.  This communication
compactness is attractive for constrained systems, but the signing path still
combines quaternion arithmetic, four-dimensional lattice routines, norm
equations, candidate enumeration, and large-integer operations.

Fixed-precision arithmetic removes unbounded integer growth, but replacing a
heap object with a maximum-sized stack array does not by itself reduce total
SRAM.  In our v2 starting point, five live allocations in one
\texttt{find\_uv} invocation total \num{6339868} bytes, about 11.9 times the
RP2350's \num{532480}-byte SRAM.  The central systems question is therefore
which values must coexist, not merely which allocator stores them.

This paper studies four questions:

\begin{enumerate}[label=Q\arabic*.,leftmargin=3em,itemsep=0pt,topsep=0.4em]
  \item Can a complete deterministic SQIsign v2 Level-I KeyGen/Sign/Verify
        path run in RP2350 on-chip SRAM without GMP, a heap, or external
        PSRAM?
  \item Can the resident table of full-precision candidate norms be removed
        while preserving the reference comparison and search order?
  \item What are the accompanying SRAM, stack, flash, time, and
        side-channel observations, and which conclusions do they support?
  \item Does lifetime scheduling remain useful after the substantial v3
        redesign, where the v2 candidate table no longer exists?
\end{enumerate}

Our contributions are as follows.

\begin{enumerate}[leftmargin=2.2em]
  \item We formulate protocol workspace placement as an aligned storage
        allocation problem over typed objects and path-sensitive lifetimes.
        Reviewed lifetime annotations are translated into C unions, offsets,
        and static assertions.
  \item We introduce an order-preserving norm sketch for the v2 candidate
        table.  It reduces resident state while retaining a full-precision
        fallback whenever the sketch alone cannot decide an ordering.
  \item We validate the v2 construction with source-correspondence and
        lifetime audit records, sanitizer and guard tests, ELF audits, two
        fresh-process repetitions of a 100-request differential experiment,
        fixed-image operation-PSP analysis, and RP2350 measurements.
  \item We transfer lifetime scheduling, but not the v2 norm sketch, to two
        v3 functions.  We test all three official parameter sets on the host
        and in Arm object builds, and report one commit-pinned \texttt{p324\_3}
        target path.
  \item We evaluate implementation security separately from functionality
        and memory.  The measured implementations remain variable-time, and
        no analog trace experiment has been performed.
\end{enumerate}

\section{Related Work}
\label{sec:en-related}

Reusing storage for noninterfering lifetimes is an established compiler and
memory-allocation principle.  Graph-coloring register allocation represents
simultaneously live values by interference edges\cite{chaitin-1981}, and
compile-time memory allocation has considered differently sized objects
\cite{gergov-1999}.  We do not claim to invent lifetime-based reuse.  Our
focus is its application to complete SQIsign operation closures, including
typed layout, failure paths, clearing, linked-image accounting, and a
reconstructible evidence chain.

Fixed-precision SQIsign first supplied uniform bounds of
7026/10713/14150 bits for Levels I/III/V\cite{fixed-precision-2025}.
Compact Quaternion Algorithms later reduced these values to
1665/2521/3319 bits and improved host performance
\cite{compact-quaternion-2026}.  Qlapoti and follow-up work improve the
ideal-to-isogeny translation and its analysis
\cite{qlapoti-2025,qlapoti-plus-2026,qlapoty-2026}.  These advances bound or
accelerate arithmetic objects; our v2 contribution instead targets their
simultaneous residency across the protocol.

For embedded SQIsign, pqm4 documented the difficulty of integrating the v2
signing side because of GMP and dynamic allocation\cite{pqm4-2024}.
Cortex-M work has optimized finite-field arithmetic or one-dimensional
verification\cite{m4-modarith-2025,sqisign-1d-2024}, while a complete
KeyGen/Sign/Verify implementation has been reported for larger Arm systems
\cite{sqisign-arm-2026}.  Other nearby implementations include a 32-bit
deployment study\cite{sqisign-32bit-2024}, an AVX-512 implementation
\cite{sqisign-avx512-2026}, and a pure-Rust v2 implementation that still uses
heap-backed integers\cite{sqisign-rs-2026}.  The v3 submission itself now
includes complete Cortex-M4 paths without external GMP
\cite{sqisign-spec-v3,sqisign-code-v3}.  Accordingly, the v2 on-chip result
and the v3 transfer experiment are reported as distinct contributions, not as
a performance comparison between generations.

Constant-time integer, lattice, and quaternion components for SQIsign are
active research topics\cite{ct-integer-2025,ct-lattice-2025,ct-quaternion-2025}.
Mukherjee et al. demonstrated a simple-power-analysis key-recovery route via a
secret-derived exponent in Cornacchia processing\cite{spa-2025}.  These works
show why a static address layout is not a side-channel countermeasure.  Our
timing and software-trace tests identify residual variable behavior; they
do not replace power/EM acquisition or attack reproduction.

A documented search through 2026-09-04, after the v3 release, found no prior
report combining the following v2 properties: complete KeyGen/Sign/Verify, no GMP or heap,
on-chip-only RP2350 execution, and linked-image accounting.  The public search
log records the queries, databases, inclusion criteria, and nearby
counterexamples.  This observation is limited to the documented search and
does not cover unpublished or later work.

\section{Background and Evaluation Scope}
\label{sec:en-background}

\subsection{SQIsign v2 and v3}

The v2.0.1 implementation studied here uses a two-dimensional response path,
including a chain of $(2,2)$-isogenies, and is not the earlier
one-dimensional verification setting\cite{sqisign-spec-v201}.  We fix Level
I and the RADIX32 finite-field backend.  Quaternion integers use 27 64-bit
limbs: a 1665-bit magnitude bound plus sign storage rounded to a 1728-bit
array.  Multiplication, division, GCD, square root, and modular exponentiation
operate on these fixed-capacity arrays and caller-owned workspaces.

SQIsign v3.0 changes parameters, integer representation, lattice reduction,
ideal representation, ideal-to-isogeny conversion, and response sampling
\cite{sqisign-spec-v3}.  Its official source provides complete Cortex-M4
KeyGen, Sign, and Verify paths\cite{sqisign-code-v3}.  The v2
\texttt{find\_uv} candidate table is absent from the v3 path, so the norm
sketch has no direct v3 target.  Large, sequentially used local states remain,
which motivates the separate lifetime experiment in \cref{sec:en-v3}.

\subsection{Why fixed-capacity integers}

GMP and its smaller mini-GMP implementation represent integers with
separately allocated limb arrays and grow those arrays through an allocator
\cite{gmp-manual-630}.  Mini-GMP passed the functional response checks in a
separate host experiment, but a simple 16-byte-aligned static-pool allocator
needed \num{317696} bytes for the measured 100-vector signing test set and saw
up to \num{4830} live blocks.  This host threshold is neither a mini-GMP lower
bound nor an RP2350 total.  We choose fixed-capacity arrays because their
ownership, alignment, and reservation can be audited before linking, not
because fixed capacity implies constant-time arithmetic.  Used-limb scans,
Euclid loops, comparisons, and exponentiation remain variable-time.

\subsection{Target and memory quantities}

The target is a Raspberry Pi Pico 2 with one Arm Cortex-M33 core of its
RP2350, clocked at \SI{150}{\mega\hertz}\cite{rp2350-datasheet}.  Code and
read-only data execute from internal flash; only the chip's \num{532480}
bytes of SRAM are counted as available data memory.  The builds use Pico SDK
2.3.0 and Arm GNU Toolchain 15.2.1 in Release mode.

We distinguish five quantities: operation-arena payload, guarded operation region,
linked mutable regions, reserved Process/Main Stack Pointer regions, and an
observed stack watermark.  A watermark is the overwritten extent for one
execution, not a bound.  ``Unreserved SRAM'' is computed after subtracting
the full PSP and MSP reservations, never only the observed watermarks.

\subsection{Security evaluation scope}

Functional failures include output disagreement, boundary-canary corruption,
uncleared workspace state, or an unintended allocator/GMP dependency.  For
side channels, we consider an observer of time, control flow, addresses,
power, or electromagnetic emanations.  This study records host timing and
software traces and selected RP2350 timing diagnostics.  It records no
full-Sign power or EM trace.  Constant-time execution, masking, fault
resistance, production randomness, and resistance to key recovery are not
claimed.

\section{Lifetime Scheduling Model}
\label{sec:en-formulation}

Let $O=\{o_1,\ldots,o_n\}$ be the operation objects and $\mathcal{T}$ the set
of allowed traces, including retry and failure returns.  Object $o_i$ has
size $s_i$, alignment $a_i$, type $\tau_i$, and a secrecy attribute.  Its
live points on trace $t$ are $L_i(t)$.  We define the interference graph
$\mathcal{G}=(O,E)$ by
\begin{equation}
  (o_i,o_j)\in E
  \quad\Longleftrightarrow\quad
  \exists t\in\mathcal{T}:L_i(t)\cap L_j(t)\neq\varnothing .
  \label{eq:en-interference}
\end{equation}
Thus, disjointness on one successful execution is insufficient.

For offsets $x_i\geq0$, a valid typed placement satisfies
\begin{align}
  x_i &\equiv 0 \pmod{a_i}, \\
  (o_i,o_j)\in E &\Longrightarrow
  (x_i+s_i\leq x_j)\ \lor\ (x_j+s_j\leq x_i).
  \label{eq:en-placement}
\end{align}
The arena height is $M_{\mathrm{arena}}=\max_i(x_i+s_i)$.  We do not solve
the general optimization problem.  Reviewed phase annotations yield a
feasible first-fit placement, emitted as typed C unions/structures with
\texttt{sizeof}, \texttt{offsetof}, alignment, and static-assert checks.

For pre/post guards $g_{\rm pre},g_{\rm post}$, PSP and MSP reservations
$R_{\rm PSP},R_{\rm MSP}$, and other exclusive mutable state $R_{\rm other}$,
the firmware quantity is
\begin{equation}
 R_{\rm excl}=(M_{\rm arena}+g_{\rm pre}+g_{\rm post})
 +R_{\rm PSP}+R_{\rm MSP}+R_{\rm other}.
 \label{eq:en-exclusive}
\end{equation}
For v2 these terms are \num{172080}, 128, \num{131072}, \num{8192}, and
\num{9936} bytes, giving \num{321408} bytes.

Two objects may share an offset only when their reviewed contracts establish:
(i) disjoint lifetimes on success, retry, and failure paths; (ii) no pointer
escape or returned reference; (iii) required clearing before reuse;
(iv) typed aliasing and alignment; and (v) cleanup on every return edge.  ABI
probes, \texttt{-Wvla -Walloca -Werror}, ASan/UBSan, canaries, zeroization
tests, and ELF audits provide complementary checks.  They do not
constitute whole-program alias verification.

KeyGen, Sign, and Verify also share one operation arena because the embedded
API serializes them.  This makes the reservation their maximum rather than
their sum.  Reentrancy, concurrent signing, and cross-core use are outside
the API contract.

\section{The v2 Method}
\label{sec:en-v2-method}

\subsection{Reducing resident state}

The starting \texttt{find\_uv} stores candidate vectors, full-precision
norms, quotients, row counts, and sorting records simultaneously.  We apply
the following transformations in sequence, checking differential transcripts
after each transformation:

\begin{enumerate}[leftmargin=2.2em]
  \item pack each four-coordinate candidate in \texttt{int8\_t[4]} after
        verifying that each coordinate lies in $[-2,2]$;
  \item sort a \texttt{uint16\_t} index permutation rather than candidate
        copies;
  \item reconstruct per-candidate quotients at their use sites;
  \item stream two rows instead of retaining all seven;
  \item move large variable-length locals into caller-owned typed workspaces;
  \item overlay ML2, candidate, fixed-degree, theta, discrete-log, inversion,
        and integer-temporary phases where the lifetime contracts permit it;
  \item share the serialized KeyGen/Sign/Verify owner; and
  \item replace the two full-precision norm rows with compact sketches and a
        full-precision fallback.
\end{enumerate}

prevents a change of storage class from being misreported as reduced total
memory.

\subsection{Order-preserving norm sketch}
\label{sec:en-sketch}

For a candidate $v$, the positive integer norm $N(v)$ can be reconstructed
from its retained packed coordinates, the row Gram matrix $G_j$, and adjusted
norm $d_j$.  Let
\begin{equation}
 \ell(n)=\begin{cases}0,&n=0,\\ \lfloor\log_2 n\rfloor+1,&n>0,
 \end{cases}
\end{equation}
and, for $w=64$,
\begin{equation}
 h_w(n)=\begin{cases}
 n,&\ell(n)\leq w,\\
 \left\lfloor n/2^{\ell(n)-w}\right\rfloor,&\ell(n)>w.
 \end{cases}
\end{equation}
The resident sketch is $S_w(n)=(\ell(n),h_w(n))$.  Candidate comparison uses
bit length, the retained 64-bit prefix, reconstructed full-precision norms on
a sketch tie, and the original enumeration index, in that order.

\begin{proposition}[Order preservation]
\label{prop:en-order}
Suppose $N(v_i)$ can be reconstructed with full precision for every retained
candidate.  The sketch comparator orders candidates as the lexicographic key
$(N(v_i),i)$ does.
\end{proposition}

\begin{proof}
Integers with different bit lengths have the same order as their lengths.
For equal lengths and unequal 64-bit prefixes, the most significant differing
bit lies in a retained position, so the prefix decides the integer order.  If
both sketch fields agree, the comparator reconstructs and compares the two
full-precision integers.  It uses the enumeration index only when those
integers are equal.  These cases cover every pair.
\end{proof}

For example, $2^{100}$ and $2^{100}+1$ have equal sketches but are sent to
the reconstruction path.  Correctness therefore does not depend on assuming
that sketch ties are rare.  In the attribution test set, reconstruction was
used for \num{5041} of \num{2062361} sorting comparisons
(\num{0.2444}\%); this frequency is a performance observation only.

\Cref{alg:en-lowmem-finduv} gives a compact, self-contained view of the two
central changes.  \textsc{PrepareRow} generates candidates in the reference
order and sorts their index permutation with \textsc{Compare}.
\textsc{SearchPairs} retains the reference row-pair, in-row, and congruence
orders.  The detailed source obligations and failure cases appear in
\cref{tab:en-correspondence}.

\begin{algorithm}[H]
  \caption{Order-preserving comparison and two-row \texttt{find\_uv} schedule}
  \label{alg:en-lowmem-finduv}
  \small
  \begin{algorithmic}[1]
    \Require packed candidates, row descriptors $R_j=(G_j,d_j)$, target $T$,
      and caller-owned workspace $W$
    \Ensure reference-key comparison; \textsc{FindUV-LM} clears $W$ on every exit
    \Function{Compare}{$i,j,V,S,G,d$}
      \If{$i=j$}
        \State \Return $0$
      \ElsIf{$S[i].\ell\neq S[j].\ell$}
        \State \Return $\Call{Cmp}{S[i].\ell,S[j].\ell}$
      \ElsIf{$S[i].h\neq S[j].h$}
        \State \Return $\Call{Cmp}{S[i].h,S[j].h}$
      \EndIf
      \State $n_i\gets\Call{FullNorm}{V[i],G,d}$;
        $n_j\gets\Call{FullNorm}{V[j],G,d}$
      \If{$n_i=\textsc{Fatal}$ \textbf{or} $n_j=\textsc{Fatal}$}
        \State \Return \textsc{Fatal}
      \ElsIf{$n_i\neq n_j$}
        \State \Return $\Call{Cmp}{n_i,n_j}$
      \Else
        \State \Return $\Call{Cmp}{i,j}$
      \EndIf
    \EndFunction
    \Function{FindUV-LM}{$T,\mathcal I,W$}
      \State $(s,L,R_0,\ldots,R_{r-1})\gets\Call{PrepareLattice}{T,\mathcal I,W}$
      \If{$s=\textsc{Fatal}$} \State \Return $\Call{Finish}{\textsc{Fatal},W}$ \EndIf
      \State \Call{ClearPhaseStorage}{$W$}
      \For{$j\gets0$ \textbf{to} $r-1$}
        \State $c[j]\gets\Call{PrepareRow}{j,0,W}$ \Comment{validation pass}
        \If{$c[j]=\textsc{Fatal}$} \State \Return $\Call{Finish}{\textsc{Fatal},W}$ \EndIf
      \EndFor
      \For{$j_1\gets0$ \textbf{to} $r-1$}
        \State $m_1\gets\Call{PrepareRow}{j_1,0,W}$
        \If{$m_1\neq c[j_1]$} \State \Return $\Call{Finish}{\textsc{Fatal},W}$ \EndIf
        \For{$j_2\gets j_1$ \textbf{to} $r-1$}
          \If{$j_2=j_1$}
            \State $(V_2,m_2)\gets(W.V[0],m_1)$ \Comment{diagonal alias}
          \Else
            \State $m_2\gets\Call{PrepareRow}{j_2,1,W}$; $V_2\gets W.V[1]$
            \If{$m_2\neq c[j_2]$} \State \Return $\Call{Finish}{\textsc{Fatal},W}$ \EndIf
          \EndIf
          \State $z\gets\Call{SearchPairs}{T,W.V[0],V_2,R_{j_1},R_{j_2}}$
          \If{$z=\textsc{Fatal}$} \State \Return $\Call{Finish}{\textsc{Fatal},W}$ \EndIf
          \If{$z$ is a solution}
            \If{\textbf{not} $\Call{ValidateAndPublish}{z}$}
              \State \Return $\Call{Finish}{\textsc{Fatal},W}$
            \EndIf
            \State \Return $\Call{Finish}{\textsc{Success},W}$
          \EndIf
        \EndFor
      \EndFor
      \State \Return $\Call{Finish}{\textsc{NotFound},W}$
    \EndFunction
  \end{algorithmic}
\end{algorithm}

Here \textsc{FullNorm} evaluates the full-precision quadratic form, requires a
positive quotient with zero remainder on division by $d$, and otherwise
returns \textsc{Fatal}.  \textsc{Finish} clears the complete caller-owned
workspace before returning.

\begin{figure}[ht]
  \centering
  \input{figures-en/sketch-flow.tikz.tex}
  \caption{Resident sketch and comparison path.  A tie causes reconstruction
  of both full-precision norms before the comparator returns an order.}
  \label{fig:en-sketch}
\end{figure}

Rows contain at most 624 candidates and are sorted by an in-place heapsort of
their index permutation.  If norm reconstruction fails, the comparison
callback latches a fatal status; an index order is returned only to finish the
sort, after which the entire row is rejected.  The temporary order is never
published as a successful result.

\begin{proposition}[First accepted result]
\label{prop:en-first}
For a fixed input, assume arithmetic succeeds in both implementations and the
correspondences in \cref{tab:en-correspondence} hold.  The proposed search
returns the same first accepted tuple as the reference, or both return
\textup{\textsc{NotFound}} within the reference search domain.
\end{proposition}

\begin{proof}
By \cref{prop:en-order}, each reconstructed row has the reference candidate
order.  A validation pass retains only row counts, and the search pass
reconstructs rows deterministically.  The row-pair, in-row, and congruence
orders are the same by \cref{tab:en-correspondence}; hence both searches first
accept the same tuple or exhaust the same sequence.
\end{proof}

This result is conditional on the source correspondence at those commits.  It is not a
formal proof of all C behavior.  The source audit is therefore combined with
12 reference/proposed transcripts, the two 100-request differential runs, an
intentional sketch-tie test, and NotFound, retry, fatal, guard, and clearing
tests.

\section{Transfer to SQIsign v3}
\label{sec:en-v3}

The official v3 \texttt{p324\_3/m4f} object reports a
\num{34816}-byte frame for \texttt{quat\_lll\_dual\_reduce\_ideal}.  We call
the implementation with changes only to this function the \emph{one-function
variant}.  It introduces two typed overlays:

\begin{enumerate}[leftmargin=2.2em]
  \item lattice-reduction state \texttt{fp\_ldl\_t} shares storage with the
        integer matrix \texttt{Aout}, which is first constructed after
        reduction; and
  \item \texttt{Ainv\_total}, after deriving \texttt{Aout}, shares its equal
        sized region with the later output basis \texttt{Bout}.  The still-live
        Gram matrix and transform do not overlap it.
\end{enumerate}

The \emph{two-function variant} adds a third overlay in
\texttt{protocols\_sign}: the commitment ideal's
last reference precedes the first write of the challenge-isogeny output
product.  Source-anchored audit records check those boundaries and the equal
type sizes.  The two-function variant changes ownership and placement in two
functions; it does not change the API, algorithms, branch conditions, or
randomness consumption.  Its source commit is \texttt{874658c6...}, based on
official v3 commit \texttt{6d017708...}.  The RP2350 firmware is tied to
harness commit \texttt{5df7acfb...}; the reported build contains no
uncommitted source or harness changes.  Reconstruction patches and SHA-256
bindings for the generated source, binary, and target record are public.

This transfer remains local.  It does not establish an automatic whole-v3
placement, and the two-function image retains 19 compiler-reported dynamic
frames.  A separate \emph{fixed-frame analysis build} is used to study stack
bounds; its results do not transfer to the two-function binary.

\section{Evaluation Method}
\label{sec:en-evaluation}

\subsection{Version isolation}

Each executable is built independently from a pinned source commit without
sharing object files across variants.  Within-v3 comparisons use the same
official base, parameter set, toolchain, and options.  Cross-generation timing
or PSP differences are descriptive only because parameters, algorithms,
integer backends, and memory ownership change together.  In particular, the
explicit v2 arena and the v3 PSP watermark are not subtracted as though they
were the same resource.

\subsection{Functional validation}

For v2, 12 fixed transcripts compare the full-norm-table and proposed
implementations.  One ordinary-API process and two separately started
low-memory processes each consume all 100 official v2 Level-I requests.  Each vector
checks public/secret keys, signed message, post-RNG state, successful Open,
one-bit modified-signature rejection, guards, and terminal clearing.  All
three generated response streams are byte-identical.  The expected response
is produced by the ordinary path at the same compact-source commit.  The two
low-memory runs therefore test fresh-process repeatability, but do not provide
independent oracles.  This is a differential-conformance test using official
requests, not a historical-response KAT.

For v3, official and two-function builds each pass the NIST API test, scheme self-test,
and 100 official-response vectors for \texttt{p324\_3}, \texttt{p500\_27},
and \texttt{p664\_17}.  This is 300 distinct parameter-set/request pairs run
once on each implementation, or \num{600} implementation-vector runs in
total.  The one-function variant additionally has five interleaved
official/adapted target pairs and a 10-vector experiment in two linked-code
placements.  The two-function variant's target evidence is one
commit-pinned \texttt{p324\_3} vector-0 KeyGen/Sign/Verify run.  These test sets are
finite regression tests, not all-input equivalence proofs.

\subsection{Stack method}

The v2 stack analysis uses 126 GCC stack-usage files with 1154 records and no
dynamic record.  It resolves every linked, input-dependent Thread-mode path
from the three operation roots, including indirect calls and manually bound
assembly/runtime frames.  Two recursive components halve their length at
each child; with maximum length 248 they have at most nine active frames.  A
source, constant, object, or function-body digest change stops the audit.

The longest condensed-call-graph path receives a conservative 212-byte
allowance for one maximum Secure Armv8-M exception entry
\cite{arm-stack-sizing-2016}.  The result concerns the operation PSP.  Handler
software uses the MSP and is not included; neither are the enabled-interrupt
set, nesting policy, or live MSP at entry.

The separate v3 fixed-frame analysis build follows the same pattern after replacing 19
dynamic frames with fixed-capacity frames.  It closes the linked operation
roots, but retains 18 indirect callback sites in candidate interrupt-handler
paths.  Hence neither the v2 nor fixed-frame result is a whole-program,
interrupt-inclusive stack bound.

 \num{77168}+\max(\num{94912},\num{14024})=\num{172080}\ \text{bytes}.
\end{equation}
The full-norm-table baseline is \num{353008} bytes, so the reduction is

\section{Side-Channel Findings}
\label{sec:en-sca}

A fixed arena removes allocator-address variation but does not make loop
counts, branches, or memory accesses independent of secrets.  The v2 path
still contains sketch-tie reconstruction, variable candidate search,
rejection, used-limb scans, early-return comparison, Euclid loops, and
secret-derived modular exponents.

For v2, two reversed-order fixed-versus-random host timing tests, 64 samples per class
each, give first-order statistics 3.570 and 3.576 and centered second-order
statistics $-5.410$ and $-5.374$.  Both second-order values cross the commonly
used $|t|>4.5$ exploratory threshold\cite{schneider-moradi-2016}.  This small
test detects a repeatable distributional difference; a value below the
threshold would not certify nonleakage.  Full-Sign software traces also show
reproducible edge and effective-address differences when signing randomness
changes.

The known SPA route targets secret-derived exponents during Cornacchia
processing\cite{spa-2025}.  In our 12-seed v2 test set, Sign reaches the
Cornacchia modular-square-root path 361 times, 190 in the modulus class that
directly matches the published exponent relation.  An isolated RP2350 powmod
diagnostic has correlation 0.999860 between exponent Hamming weight and time,
with an approximate slope of 4.004 ms per set bit.  This is a timing
diagnostic, not an analog trace or a full-Sign key-recovery experiment.

For v3, a fixed-message, fixed-signing-randomness, fixed-key-address test
uses ten official keys in two key orders.  Across official and one-function host builds,
\num{\VThreeFixedTimingRows} verified signatures reproduce key-associated
median rankings; the minimum between-order Spearman coefficient is
\num{\VThreeKeyTimingSpearmanMin}.  The corresponding RP2350 experiment
collects \num{\VThreeTargetFixedTimingSamples} verified signatures with cache
normalization; both implementations have rank coefficient
\num{\VThreeTargetKeyTimingSpearmanMin} and key-median spans of
\num{\VThreeTargetKeyTimingSpanMinPercent}--\num{\VThreeTargetKeyTimingSpanMaxPercent}\%.
Public and secret key components change together, so the result is
key-associated timing, not secret-only attribution.

\section{Discussion}
\label{sec:en-discussion}

\subsection{Transferability and RAM--stack--flash--time trade-offs}

The common element across v2 and v3 is the procedure for identifying typed
objects, establishing noninterference from their lifetimes, and making the
resulting storage reuse explicit in C.  The v2 norm sketch, 1665-bit integer
bound, and \num{172080}-byte arena are version-specific.  The v3 results show
that the placement procedure applies to different local states, but do not
establish generality beyond the two SQIsign functions and three parameter sets
tested here.

The v2 firmware leaves \num{211072} bytes unreserved, compared with
\num{30144} bytes for the full-norm-table baseline.  This is integration
capacity rather than demonstrated capacity for a particular combination of
randomness, communications, interrupts, and countermeasures.  Constant-time
or masked implementations may require additional state and fresh randomness,
so their memory and security costs must be evaluated together.  For v3, only
local stack changes were measured; an exclusive-SRAM total comparable to the
v2 accounting is not available.

\subsection{Annotation-driven layout generation}

Each layout annotation specifies phases, size, alignment, secrecy,
pointer-escape status, and clearing events.  The generator constructs an
interference graph, assigns aligned offsets by first fit, and emits JSON,
Graphviz, typed C unions/structures, and static assertions.  For the v2
\texttt{find\_uv} annotations, it reproduces the \num{172080}-byte layout, and
the generated header matches the size and offsets of the Arm workspace types.

A coverage check enumerates all \LifetimeAnnotatedObjects{} declared physical
members and \LifetimeDirectAccessForms{} direct member or whole-phase access
forms; an unannotated member or direct access is rejected.  The generator does
not infer phase meaning or lifetimes from C, nor does it establish the absence
of indirect aliases, pointer escape, missing failure-edge cleanup,
function-pointer targets, or optimization-induced changes.  Its guarantees
therefore depend on annotation completeness and are supplemented by lifetime
audit tables, canaries, zeroization tests, and ELF audits.

\section{Limitations}
\label{sec:en-limitations}

The evidence supports a narrower conclusion than an unconstrained ``embedded
SQIsign'' claim:

\begin{enumerate}[leftmargin=2.2em]
  \item \textbf{Target scope.}  All physical measurements use one RP2350
        board and one Cortex-M33 core.  v2 covers Level I/RADIX32.  The
        two-function variant's host response checks and Arm frames cover all
        three v3 parameter sets, but target whole-image evidence covers only
        \texttt{p324\_3}.
  \item \textbf{Input scope.}  The v2 target result repeats one deterministic
        KeyGen/Sign/Verify path twice.  Its operation-PSP analysis closes linked
        input-dependent Thread-mode paths for the fixed image, but not handler
        or MSP behavior.  The two-function variant has one target vector and
        no target timing distribution.
  \item \textbf{Functional scope.}  v2 differential tests and v3 official
        response checks use finite test sets.  The C correspondence audit and
        \cref{prop:en-first} do not form an all-input semantics proof.
  \item \textbf{Manual contracts.}  The coverage check catches declared-member
        and direct-access omissions, but phase meaning, indirect aliases,
        escape, and failure cleanup remain manually reviewed assumptions.
  \item \textbf{Stack scope.}  A whole-program, interrupt-inclusive maximum
        requires resolution of handler callbacks, enabled IRQs and priorities,
        nesting, and live MSP state.  The two-function variant additionally
        requires bounds for its remaining dynamic frames.
  \item \textbf{Security scope.}  The implementations are variable-time.
        Full-Sign power/EM traces, independent acquisitions, positive-control
        attack reproduction, masking, and a complete constant-time rewrite
        were not evaluated and are required before claiming resistance.
  \item \textbf{Practicality.}  v2 KeyGen and Sign are too slow for many
        products.  The \num{211072} unreserved bytes may accommodate system
        integration or countermeasures, but that capacity has not been
        demonstrated with production RNG, communications, interrupts, and
        countermeasure state active together.
\end{enumerate}

\section{Conclusion}
\label{sec:en-conclusion}

Typed lifetime scheduling and an order-preserving norm sketch reduce the
SQIsign v2 Level-I operation arena from \num{353008} to \num{172080} bytes.
The resulting RP2350 firmware uses no GMP, heap, or external PSRAM, reserves
\num{321408} bytes of SRAM, and leaves \num{211072} bytes unreserved.  Two
fresh-process repetitions of the official-request differential experiment,
lifetime and source audit records, linked-image audits, and fixed-image
operation-PSP analysis support this bounded result.

In SQIsign v3, three local overlays across two functions reduce all six tested
Arm frames over the three official parameter sets.  One commit-pinned
\texttt{p324\_3} target path reduces the Sign PSP watermark from
\num{101060} to \num{96396} bytes.  This transfer supports the reuse of the
lifetime-scheduling method, while the v2 norm-sketch transformation remains
version-specific.

The two-function v3 result is limited to local frame analysis and one target
path, and the annotation-driven placement depends on manually established
lifetimes.  Both generations remain variable-time, and neither has analog
resistance evidence or an interrupt-inclusive whole-program stack bound.
Accordingly, the result concerns auditable memory engineering rather than
general optimality or hardened deployment readiness.
